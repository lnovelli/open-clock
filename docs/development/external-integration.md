# External API and Hermes integration

The authoritative public API shapes, limits, errors and examples are in [README External access and security](../../README.md#external-access-and-security). Inspect the live provider and client before changing either: compatibility claims here describe the current implementation, not every installed version.

## Provider boundary

The current external transport is explicit binding to `com.openclock.AccessService` and synchronous raw Binder descriptor `com.openclock.IAccessApi`, transaction `IBinder.FIRST_CALL_TRANSACTION`. It is not the removed ordered-broadcast API or Android's standard `AlarmClock` intent provider. The caller needs package visibility; invoke off the UI thread, read the exception before the JSON string, handle bind/death/disconnection and unbind. Clients that need to defend against a substituted provider must verify the provider signer: the package name alone is not authentication.

Capture `Binder.getCallingUid()` on the Binder thread and resolve identity on every transaction. Current policy requires exactly one installed package and current signer, binds approval to identity including installation time, and rejects ambiguity/shared UIDs and unavailable credential-protected storage. Package visibility is security-relevant; review the manifest's broad visibility and distribution implications. Unknown callers are denied before request parsing or dispatch. A notification action opens a token-validated unlocked review; it cannot grant access itself. Approval is full read/write, and rejected calls are discarded, not queued. Revocation is serialized with operations: an admitted request can finish, later requests are denied. Fail closed on access-storage failures; a failed write/revocation is not proof of durable revocation.

Keep strict bounded JSON/envelopes and error classifications as documented. Verify actual parser behavior for duplicate keys, invalid escapes/control characters, uppercase literals, integer overflow and trailing input; a parser's lenient flag alone is insufficient proof. Preserve 64-bit IDs, unknown-field rejection and the distinction between absent fields and explicit null. No multi-request transaction or Binder idempotency key exists; a transport, storage or internal failure can follow a commit. List/reconcile state before any manual retry, especially create. Names are not unique, and list-then-update is not compare-and-swap.

Provider-side confirmation is best effort after a successful Binder commit: compare canonical before/after state and show a standard text toast on the main looper with application context for enabled creation, enabling, or enabled time/date/repeat changes, not disabled, unchanged or metadata-only writes. Use the committed trigger and warn for scheduling/access errors. Presentation must never change the mutation result; Android may suppress or rate-limit the toast.

For user-initiated read-only navigation, an explicit `com.openclock.MainActivity` intent with action `com.openclock.action.VIEW_ALARM` and data `openclock://alarm/<positive-64-bit-id>` opens the current exact alarm in the editor. It grants no Binder access and performs no mutation. Reload the exact ID, reject malformed or missing targets, preserve unsaved editor changes behind confirmation, and retain a pending target across recreation. A client must use the ID from its validated successful create reply, never a guessed label or an uncertain result. Older installed Open Clock versions do not support this navigation.

## Current Hermes client compatibility

The separately maintained Hermes Android client's `OpenClockClient`, `OpenClockActions` and `AlarmCreationConfirmation` should be reviewed at the same time as provider changes. In the inspected implementation it declares package visibility and uses the Binder interface above, but does **not** authenticate the provider signer. It serializes its own clients, validates bounded replies and rechecks authorization/cancellation just before transaction admission. A synchronous transaction already dispatched may finish after cancellation or revocation; an ambiguous result must not be replayed. A definite first `ACCESS_DENIED` requires user approval and an explicit new request.

Hermes-created alarms resolve exactly one `Hermes` group and include its ID in the initial create. Group creation and alarm creation are separate operations and not atomic across apps; duplicate group matches are rejected. The current uncertain group-create guard is process-local, not durable across restart; inspection and explicit review are necessary before retry. Preserve legacy alarms rather than deleting or silently migrating them. For selection, use a positive ID or an exact unique label/group, never guess among duplicates.

Preserve date versus weekly recurrence and Calendar weekday numbering (Sunday=1). The current relative-alarm path rounds up to whole-minute precision and rejects an ambiguous DST-overlap instant rather than misrepresenting it. Confirmation must use the validated provider reply's `nextTriggerAt` rendered in the device's current zone and offset, and the reply's label/sound/vibration, not request defaults. Missing/malformed fields, disabled state, `schedulingError` or absent trigger are not equivalent to a set alarm; even a recorded trigger is not delivery proof. A provider operation does not imply a particular remote ingress can invoke it: trace client dispatch and authorization before claiming that capability.

## Verification

Use disposable Binder/Android fakes against production provider and client code to cover strict syntax and limits, unknown caller denial before parsing, identity ambiguity, approval/revocation races, busy admission, storage failure, caller cancellation, malformed replies, no replay after dispatch, duplicate names and concurrent group creation. Test date/recurrence/relative DST semantics, response-sourced confirmation, missing fields, disabled/error states and DST overlap; compare provider canonical state around toast eligibility. Inspect both manifests and build affected APKs. Such probes do not prove Android Binder identity, approval UI, toast display, alarm delivery or signer/device integration; actual device tests need explicit authorization.
