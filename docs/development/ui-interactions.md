# UI and interaction development

Read the current phone and Wear activities, `AlarmPresentation`, resources and [README](../../README.md) before changing interactions; source and product behavior may evolve. A build or host fixture does not establish physical layout, key routing, gesture delivery or toast visibility.

## Phone

- Follow the system light/dark theme for the list and access screens; inspect both resource variants and programmatic colors. Keep the intentional dark-violet ringing presentation readable, including system-bar icons. Preserve editor drafts/baselines, active occurrence and selected snooze across recreation.
- Keep alarm rows compact and readable with accessible toggle targets; a group heading/chevron needs a generous touch target and state-specific accessibility label. Preserve list scroll across switches, refreshes, editor return and recreation. If a `ScrollView` must be rebuilt, restore its offset after measurement and reject stale callbacks or intermediate zero offsets during overlapping refreshes.
- New phone/watch drafts use the current hour and minute, sound off and vibration on; preserve existing and explicitly selected values. The current minute can resolve to tomorrow. Saving an existing edit enables/schedules it subject to access; the list switch remains the disable path. Show committed pending snoozes and scheduling errors without implying registration or delivery.
- Phone group enable confirmation summarizes the earliest committed trigger rather than emitting a toast for each alarm. UI and external confirmation paths have different admission rules; see [alarm-engine.md](alarm-engine.md) and [external-integration.md](external-integration.md).

## Wear

- Preserve phone/watch ownership throughout create/edit/navigation. Back moves one step within a multi-step flow and exits from the list; dialogs and keyboard get their own Back first. Handle activity swipe-to-dismiss consistently with page Back while ignoring stale callbacks; system Home/power remains system-controlled. Keep drafts across Back and recreation.
- Preserve the watch time-then-customize creation flow, visible Save, editable label/date/sound/vibration, row tap-to-edit, long-press actions and the separate enable switch. A month/day choice resolves to a concrete next future date, including leap-day handling; reject a selected DST-gap occurrence rather than silently moving it to another year. Phone-owned changes need an acknowledgement and appropriate matching snapshot; never promise a phone change from an offline watch-only alarm.
- At Save, confirm the resolved date when an explicitly chosen month/day falls in a later year or differs from the previously displayed choice. Re-resolve and fence the editor draft, lifecycle and time zone after each confirmation; preserve the separate schedule-change warning and store/phone compare-and-write. An existing fixed date is not rolled forward merely because its time changed. Do not retain unconfirmed picker changes through recreation. For an unconfirmed phone enable, an apparently past cached date is only an advisory based on the watch clock/zone; never block the phone request or infer rejection from that cache. Local store validation remains authoritative.
- Round-screen ringing content needs readable time/label and accessible distinct dismiss/snooze controls with meaningful offline, mute and unconfirmed state. Measure round-safe child content at its final size during measurement rather than relying on placeholder layout sizes. Preserve exact tokens, snooze eligibility, requested Back/notification-clear dismissal and phone acknowledgements.
- Preserve swipe-delete direction: either horizontal direction on phone, physical right-to-left on watch, with the other watch direction reserved for navigation. Keep the existing confirmation and phone mutation protocol; exclude switch-originated touches, preserve vertical scroll and accessibility, cancel child press only when a drag wins, and abort on multitouch or focus loss.
- Identical phone snapshots should not needlessly rebuild the list. Compare display-relevant state, including freshness and pending/confirmation transitions, without treating publication time alone as content. On tap, atomically resolve a fresh revision and verify that the alarm still matches the displayed row.

### Responsive list/editor updates

`MainActivity` renders detached `WatchUiData` prepared on `WatchUiWork.IO`: phone cache/receipt reads, local alarms/active sessions, mirror state, fallback join, grouping, next-alarm selection and display fingerprinting must not acquire engine or `PhoneSync` locks on the UI thread. Capture the phone cache and one detached local journal generation under the existing PhoneSync → AlarmStore lock order; join only when owner, epoch, revision and publication match, retaining unmatched fallback rows as uncertain. Legacy migration can require additional reads; mirror and other complication reads remain separate. Broadcasts/age ticks coalesce background reloads; identical display state does not rebuild the list or show a progress shield. Revision/publication-only changes remain advisory, but receipt coverage and freshness transitions affect the fingerprint. Android view construction/layout and permission/channel Binder reads still run on the main thread; very large lists can still jank and require device profiling.

For user-initiated display preparation, opt in to content-free timing logs by setting the Android log property `log.tag.OpenClockUiTiming` to `DEBUG`; `OpenClockUiTiming` logs display-worker queue wait, PhoneSync and AlarmStore monitor wait, time under each monitor, and total preparation time in milliseconds. Phone read time excludes nested watch wait/read; remaining preparation includes joins, mirrors and other work. These are elapsed-time measurements, not disk-only latency or rendering time; normal logging is off unless enabled. Do not log alarm labels, times, IDs or phone snapshots.

User-initiated local create/edit/toggle/delete, phone create/edit/toggle/delete, explicit phone refresh/status checks and clearing receipt status use a translucent full-window shield with an indeterminate indicator. It distinguishes watch/sync storage preparation, phone synchronization and final display preparation; it is not a byte/percentage meter. Keep the screen on while the shield is visible in the foreground; removing it restores the normal timeout, and backgrounding does not hold a wake lock. Show it before enqueueing work, never after waiting for a store lock. Block touch, Back/swipe and duplicate list/editor mutations while admitted. Phone row target capture and active-control lookup also run off-main, preserving revision/field and exact-token checks. Edit/delete compare-and-write remains inside the engine monitor on the worker; moving I/O must not split that transaction.

`WatchUiWork` is retained across configuration changes and targets only its attached started Activity. A stopped/finished window does not cancel a possibly committed write or release its admission early; work finishes and releases the process-wide gate even without a window. Returning to the same retained flow delivers completion once. Successful read-only phone-row and ringing-control lookups complete without a second display read; a changed/missing target or a refresh requested while work is in flight still refreshes as needed. Detached drafts/list scroll survive normal recreation; stale reloads cannot overwrite the completion snapshot. If saved state records an operation interrupted by process recreation, require returning to the list before saving that restored draft again. This is conservative UI fencing, not a new durable local-create idempotency journal: abrupt process death before state saving can still lose presentation-only intent. Phone uncertainty barriers remain durable and authoritative.

Phone acknowledgements still require an accepted matching epoch and a snapshot at/after the relevant revision; toggles use the validated revision actually acknowledged by the phone, including an unchanged revision for a no-op, and also require the expected enabled state. Missing or invalid acknowledgement revisions remain unconfirmed. Snapshot-before-reply works. The shield ends after observed completion or the bounded uncertainty decision (existing protocol reply wait, then up to 15 seconds for the snapshot; explicit refresh up to 25 seconds). Explicit refresh uses its own fetch pass and distinguishes request/read failure, incomplete local reconciliation, identity changes, an accepted newer snapshot and a successful unchanged read. Reading a snapshot or sending a request is not a phone publication acknowledgement; if no newer snapshot arrives, report that refresh remains unconfirmed. Timeout never proves rejection and never triggers mutation replay. Timers/storage contention and OS suspension are not hard deadlines. Unknown requests stay visibly uncertain; confirmed mutation status may be cleared on IO only after the matching snapshot or publisher replacement, never during rendering. Keep the create request ID associated with an unconfirmed editor draft so a late positive receipt cannot re-enable its Save as a second create.

`WatchApplication` replaces the watch manifest's shared `ClockApplication` entry point so startup active-session recovery and MainActivity foreground reconciliation also queue on IO rather than waiting on the engine before the first frame. Preserve the post-launch recovery boundary and never run full rescheduling on receiver-only process creation; the phone application's lifecycle is unchanged.

`PhoneSync` deadline/failure callbacks and advisory complication persistence after sync/local commits also run off-main; merely offloading `saveAlarm` while posting synchronous bookkeeping back to MAIN would leave the freeze intact. No protocol paths or store commit/token semantics change. This shield is scoped to the list/editor, not the separate ringing activities: their existing snooze/dismiss, periodic active-state checks and key/gesture paths are unchanged and can still wait on engine/mirror locks. Do not describe this as eliminating every UI-thread lock or guaranteeing rendering latency.

See [wear-sync.md](wear-sync.md) for snapshot races, offline fallback, dismissal scope and the complication. Run focused tests on real production formatters, navigation/gesture boundaries and state preservation; report separately any explicitly authorized phone/watch UI tests.
