# Alarm backend behavior

`AlarmStore` implements the shared static API. Changes are serialized on `AlarmStore.class` in the app's single process. Data is atomically written and synced to a device-protected, backup-excluded JSON file; reads fail closed on unreadable/corrupt storage rather than replacing it with an empty list.

## Data and edits

- Create requires `hour` and `minute`. Defaults: enabled/vibrate/snoozeEnabled true, sound false, snoozeMinutes 5, snoozeCount 3, vibrationPattern `basic`, empty label/days, null date/groupId. Edits merge omitted public fields; private input fields are ignored.
- Label, group, sound, vibration and snooze-configuration edits preserve **all** persisted runtime fields: pending generation/time, concrete one-shot date, consumed weekly occurrence, active session, pending snooze and its count. They do not replace or cancel the pending schedule, even while ringing/snoozed. Changing hour/minute/date/days/enabled deliberately resets the occurrence/session and schedules a fresh generation if enabled. Editing a fired one-shot's label does not re-enable or recreate it.
- `snoozeCount: 0` means unlimited snoozes for that occurrence. Otherwise it counts successful snoozes, not the initial ring. Minutes: 1–1440; count: 0–1000. Snooze commits a replacement pending generation before removing the active session; failed persistence retains both prior controls and prior weekly schedule.
- `vibrationPattern` is a string enum: `basic`, `pulse`, `heartbeat`. Missing legacy values read/default to `basic`; other supplied values are rejected. The alarm editor and external API expose this setting.
- Date uses strict ISO `yyyy-MM-dd`; days use Calendar Sunday=1 through Saturday=7. A date and non-empty weekdays are mutually exclusive. Empty days means one-shot, **not daily**. A date-less one-shot internally records its chosen occurrence date, so restoration cannot turn a missed alarm into tomorrow's alarm.
- Device local timezone applies. Explicit dates in a DST gap are rejected on enabling; date-less/weekly schedules skip nonexistent local times. Search extends through 370 calendar days, including the fortnight needed when the next selected weekly day is a DST gap. Repeated DST times use the first offset still in the future; a consumed weekly date is not replayed in the second offset. Scheduled occurrence dates are persisted so delayed delivery across a timezone change does not relabel the consumed date.
- Limits: 500 total records, **450 enabled alarms**, 100 groups; labels 200 and group names 100 characters. The enabled cap reserves headroom below common 500-registration OEM limits for recovery and tentative replacements. Existing over-cap stores are not destructively truncated; they may need alarms disabled if the device refuses registrations. Deleting a group only clears member groupId.

## Scheduling and reconciliation

- Creating, enabling or changing an enabled schedule requires exact-alarm access, notification permission, app notifications enabled, and a High-importance ringing channel. No inexact fallback. Metadata edits, disabled saves, deletion and dismissal remain available without those permissions.
- Public JSON includes `nextTriggerAt` (epoch milliseconds, 0 if no pending trigger), `snoozedUntil` (epoch milliseconds, 0 if no snooze is pending), and `schedulingError` (text or null). A pending snooze may remain visible after registration fails. `enabled` preserves user intent after permission-related restore failures and is not by itself proof of a registered schedule. Reads surface current permission failures.
- Exact alarm-clock PendingIntents carry ID+unique generation in both identity URI and extras. Fire/dismiss/snooze reload persisted generation/session; stale deliveries are harmless. New schedules are registered before atomic commit; failed persistence cancels only the tentative generation. Old schedules are canceled only after successful commit.
- Reconciliation commits and retires replacements **one alarm at a time**, never staging a second complete schedule set. Unchanged future/due generations are reinstalled without token churn or unnecessary disk commits. An OS registration failure retains the original generation rather than canceling a potentially valid schedule, and surfaces an error.
- A queued trigger already due by less than ten minutes retains its exact generation and occurrence. It is reinstalled for prompt delivery, not recomputed as tomorrow/next week. Older missed one-shots/snoozes expire rather than silently rolling over; older missed weekly occurrences advance to the next valid date. Ordinary delivery is subject to the same ten-minute catch-up limit.
- If a weekly occurrence fires but registering its next occurrence fails, the current active session and consumed date are still committed, with an error, no pending token/time, and a private durable `_retryAt` five minutes later. Dismissing/expiring that session does not discard the retry. Recovery retries reconciliation when due; another registration failure renews the five-minute deadline, and successful preparation clears both retry and error while scheduling the next unconsumed occurrence. Metadata edits preserve retry state; disabling/deleting the alarm stops it. A failed atomic commit keeps the prior persisted state and cancels any tentative new generation rather than reporting scheduling success.
- Boot/locked boot, package replacement, wall-clock/timezone changes and exact-access grants reconcile pending schedules. MainActivity lifecycle reconciliation is supplied by ClockApplication without editing MainActivity. Process creation **never** reconciles pending generations before the launching receiver can consume them.

## Direct boot and process recovery

- Active sessions persist the platform boot count and monotonic start time, as well as a wall-clock timestamp. A later BOOT_COMPLETED after first unlock does not dismiss an alarm that started during the same locked boot. Prior-boot/legacy-unidentified sessions expire. Pending snoozes remain separate and restore normally.
- A single private alarm-clock recovery PendingIntent is armed before committing pending schedules or new active sessions. Before commit its deadline covers both the old and proposed state, so failed persistence cannot strand the prior state. It wakes about 30 seconds after the earliest pending trigger, or every 30 seconds while a valid session exists.
- Recovery consumes only due persisted generations and restarts still-valid sessions; it does not churn every future schedule on each watchdog wakeup. A tokenless weekly retry shares this same recovery registration, so reopening the app is not required. Once no session is active, its wake follows the retry deadline; an already-overdue deadline is backed off five minutes when arming, including when a failed storage commit prevented renewal. This avoids an unbounded one-second wake loop. Thirty-second active-session recovery remains bounded by the ten-minute elapsed session limit. Persistent registration/storage failure can continue five-minute background retries until success, disable/delete, or loss of exact access. This repairs a process gap between the fire commit and foreground-service startup, as well as later service loss. ClockApplication additionally posts active-only recovery after process creation. START_STICKY service reconstruction remains in place.
- Recovery itself uses `setAlarmClock`, not a Doze-throttled ordinary exact alarm. It occupies **one shared registration** and can appear as the system's next-alarm indicator, including 30-second recovery deadlines while ringing. It also incurs bounded periodic wakeups during the ten-minute ringing window. Recovery is an OS-mediated retry, not a guarantee of an exact 30-second restart under OEM restrictions.
- Session expiry is ten elapsed minutes on the same boot, unaffected by wall-clock edits. Reconstructed notifications use only the remaining session lifetime rather than restarting their ten-minute timeout.

## Ringing

A private foreground media-playback service handles independent simultaneous alarm sessions and persistent dismiss/snooze actions. Sound and vibration have independent deterministic owners: the **lowest alarm ID** among active alarms requesting that output. Once that alarm stops/disables the output, the next eligible ID takes over. Vibration pattern changes apply while ringing; all other alarms retain their own controls and snooze state.

Waveform timings in milliseconds (alternating off/on, repeating from index zero):

- basic: `[0, 600, 400, 0]`
- pulse: `[0, 150, 150, 150, 550, 0]`
- heartbeat: `[0, 100, 120, 250, 900, 0]`

The system alarm ringtone is used with a bundled local fallback if opening that ringtone fails. Audio uses the alarm stream, delayed audio-focus support, and a five-second retry after denied/lost focus; a missing/failed player retries and an unfinished prepare is retried after ten seconds. Stale player/focus callbacks cannot modify a replacement player's state. No volume or DND override is requested; vibration respects DND. Notification channels themselves do not automatically sound/vibrate, avoiding per-alarm silent-setting bypass.

The private alarm Activity supports lock-screen display without dismissing the secure keyguard, using API-26 window flags and guarded API-27 methods. Android 14 full-screen intent access is checked: without it, notification controls remain the fallback. A denied foreground-service launch posts visible controls plus an explicit warning; continuous audio cannot be promised then. The service uses a bounded wake lock and releases audio/vibration on shutdown.

## Manifest / IPC ownership

Launcher: `com.openclock.MainActivity`. Since 1.3, the old exported ordered-broadcast receiver is removed; the separate authenticated JSON Binder service is `com.openclock.AccessService`. See README for the current transport and approval rules. The standard `android.intent.action.SET_ALARM` filter is not advertised.

## Verification boundaries and residual limitations

Focused host checks execute the actual AlarmStore/AlarmTimes code against a temporary fake Android platform and real local atomic-file/JSON operations; they cover DST, runtime-preserving edits, quota-bound replacement, injected scheduling/storage failures, due generations, snooze/occurrence state, boot identity, monotonic expiry and recovery admission. A focused weekly-retry probe also covers failed next registration, no early retry, renewed backoff, successful future scheduling, fire/retry/recovery-registration rollback, session expiry, metadata preservation and disable/delete cleanup; it reproduced and checked the fix for the overdue-retry/storage-failure one-second wake loop. Retry deadlines/session ages were seeded to exercise due/expired paths without waiting five/ten real minutes. Separate host checks invoke actual compiled RingingService focus retry and waveform methods. These checks are **not Android device tests** and no unit-test files were added to the repository. Offline Gradle APK builds are available.

No Android device is available: actual exact/Doze delivery, reboot/unlock delivery, OEM background limits, audio focus and playback, vibration/DND, API-26 lock-screen display, permission dialogs and real process termination remain unverified. Force-stop/uninstall, disabled permissions/channels, alarm volume zero, DND and OEM restrictions can prevent alerts. Full-screen intent access is optional and user/system controlled.

A process killed after registering a tentative generation but before committing/canceling it can leave an orphan OS registration until it fires; generation validation prevents a false alert, but repeated crashes can consume the reserved quota headroom. There is no transactional primitive spanning disk and AlarmManager. Recovery also depends on retained exact-alarm access and the OS delivering its wakeup; blocked foreground startup provides controls, not guaranteed continuous sound. Large time/zone changes still require serialized per-record durable commits; slow-device reconciliation latency has not been measured.
